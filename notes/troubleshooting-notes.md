# Troubleshooting Notes — Lab 64 Accessibility Features Persistence Investigation

## 1. Real Accessibility Binaries Were Not Modified

### Decision

The lab did not replace or modify:

```text
C:\Windows\System32\utilman.exe
C:\Windows\System32\sethc.exe
```

or the other accessibility binaries.

### Reason

Changing these files can interfere with Windows functionality and could create a real persistence mechanism.

### Resolution

The persistence behavior was simulated through a separate Registry key.

## 2. Native Accessibility IFEO Entries Were Not Found

### Observation

The targeted checks for:

```text
utilman.exe
sethc.exe
```

did not return suspicious configuration values.

The broader accessibility verification also did not establish entries for:

```text
utilman.exe
sethc.exe
osk.exe
magnify.exe
narrator.exe
```

### Interpretation

No native accessibility-specific IFEO persistence was established.

## 3. Existing IFEO Entries Were Present

### Observation

The native IFEO enumeration returned multiple entries.

### Interpretation

The mere existence of IFEO entries does not prove persistence or malicious behavior.

Legitimate software may use IFEO for debugging, compatibility, diagnostics, or other purposes.

### DFIR Lesson

An analyst must investigate:

```text
Target
+
Debugger
+
Path
+
Signature
+
Hash
+
Process
+
Context
```

rather than treating every IFEO key as malicious.

## 4. WOW6432Node IFEO Entries Were Present

### Observation

The 32-bit IFEO Registry view contained several entries.

### Interpretation

This is configuration data requiring contextual analysis, not an automatic persistence finding.

## 5. Safe Registry Simulation

### Problem

A real accessibility persistence mechanism would be unsafe to create for this lab.

### Resolution

A separate key was created:

```text
HKLM:\SOFTWARE\Lab64-AccessibilityPersistence
```

with:

```text
Simulated Debugger = C:\Lab64\simulated-payload.exe
```

### Benefit

This allowed the investigation workflow to be practiced safely without modifying the real IFEO configuration.

## 6. PowerShell Event ID 4104 Provided No Relevant Result

### Observation

The search for:

```text
Lab64-AccessibilityPersistence
SimulatedDebugger
```

returned no relevant result.

### Interpretation

The Registry modification was not independently established through the supplied PowerShell Script Block Logging.

### DFIR Lesson

A missing 4104 event does not prove a command was never executed.

## 7. Security Event ID 4688 Provided No Relevant Result

### Observation

The PowerShell search returned no relevant 4688 result.

### Interpretation

Security process-creation telemetry did not independently support the Registry modification.

### Resolution

The investigation relied on direct Registry verification and available Sysmon process telemetry.

## 8. Sysmon Event ID 1 Was Available

### Observation

PowerShell-related process creation events were observed:

```text
28-08-2026 06:36:37
28-08-2026 06:36:35
28-08-2026 06:35:36
```

### Limitation

The supplied event output did not provide enough detail to connect one specific event to the Registry change.

### DFIR Lesson

Temporal proximity alone is not sufficient attribution.

## 9. Sysmon Event ID 3 Was Available

### Observation

Numerous network events were present.

### Interpretation

Network monitoring was operational.

### Limitation

No event was established as being generated by the lab Registry artifact.

## 10. Lab Registry Artifact Cleanup

### Observation

The lab-only Registry key was removed successfully.

Cleanup command:

```powershell
Remove-Item `
"HKLM:\SOFTWARE\Lab64-AccessibilityPersistence" `
-Recurse `
-Force
```

Verification:

```powershell
Test-Path "HKLM:\SOFTWARE\Lab64-AccessibilityPersistence"
```

Result:

```text
False
```

### DFIR Lesson

Any controlled persistence simulation should have an explicit cleanup and verification stage.

## 11. Accessibility Binary Integrity

### Observation

All five accessibility binaries returned:

```text
Valid
```

for Authenticode status.

### Interpretation

The baseline did not show evidence that the Windows accessibility executables had been replaced with unsigned files.

## Troubleshooting Summary

| Observation | Resolution |
|---|---|
| Real accessibility persistence was unsafe | Used a lab-only Registry key |
| Native accessibility IFEO entries not established | Documented clean baseline |
| Existing IFEO entries found | Treated as configuration requiring context |
| WOW6432Node entries found | Treated as supporting Registry context |
| 4104 no relevant result | Documented telemetry limitation |
| 4688 no relevant result | Documented telemetry limitation |
| Sysmon 1 available | Used as supporting process telemetry |
| Sysmon 3 available | Used as network context |
| Real Windows binaries unchanged | Verified signatures and metadata |
| Lab Registry artifact created | Verified simulated debugger |
| Cleanup completed | `Test-Path` returned `False` |

## Final Troubleshooting Lesson

The key lesson from Lab 64 is:

> A persistence investigation can be practiced safely without creating the actual persistence mechanism.

The correct approach is:

```text
Baseline
   +
Inspect
   +
Simulate Safely
   +
Collect Evidence
   +
Correlate
   +
Clean Up
   +
Verify
```

This preserves both system safety and investigative value.
